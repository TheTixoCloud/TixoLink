# TixoLink NEXUS 1.0.0-rc2 — Release Candidate

**Status: RELEASE CANDIDATE.** Builds on `1.0.0-rc1` with a public
one-command installer and a updater fix discovered while building it. It
has not been exercised in production. CLI flags and the on-disk
configuration schema may still change before the final `1.0.0`.

## What's new since 1.0.0-rc1

- **Public one-command bootstrap installer (`TixoLink.sh`).** A small,
  auditable root-level script gives new users a single install command:

  ```
  TIXOLINK_CHANNEL=rc bash <(curl -fsSL https://raw.githubusercontent.com/TheTixoCloud/TixoLink/master/TixoLink.sh)
  ```

  and a single launch command afterwards:

  ```
  tixolink
  ```

  It checks the host (root, supported OS, amd64, HTTPS-capable curl),
  resolves and downloads the selected GitHub Release artifact, verifies
  its SHA256 checksum and internal archive structure *before extracting
  anything*, and then delegates the actual install/upgrade/downgrade
  decision to that release's own `install.sh` — the same authoritative
  lifecycle `tixolink update apply` already uses. It does not duplicate
  the application installer, does not run a second unverified script,
  and does not clone the repository. See "Public bootstrap installer" in
  [docs/lifecycle.md](../lifecycle.md) for the full design and trust
  model, which is identical to the existing updater's.

- **Release channels.** `TIXOLINK_CHANNEL=stable` (default) only ever
  installs a non-prerelease GitHub Release, and fails closed rather than
  silently installing a prerelease if none is published yet.
  `TIXOLINK_CHANNEL=rc` installs the latest published release candidate.
  `TIXOLINK_VERSION=X.Y.Z[-rcN]` installs an exact version. Because there
  is no stable `1.0.0` yet, the public install command during the RC
  period uses `TIXOLINK_CHANNEL=rc` (or an exact `TIXOLINK_VERSION`)
  explicitly — plain `bash TixoLink.sh` with no override will refuse,
  by design, rather than quietly treating a release candidate as stable.

- **Fixed: `tixolink update apply` release-asset name mismatch.**
  `modules/update.sh` was looking for a checksum asset named
  `checksums.sha256`, but the actual release packaging
  (`packaging/build-release.sh`) — and the already-published
  `v1.0.0-rc1` GitHub Release — names that asset `SHA256SUMS`. This made
  every real `update apply` against a published release silently fail at
  asset selection; it was only ever exercised against a self-consistent
  test fixture that happened to share the (wrong) name. Discovered while
  building `TixoLink.sh` against the real release layout and fixed in
  this release, with a new regression test
  (`test_apply_succeeds_with_real_asset_naming`).

## GRE security warning

**GRE (IP protocol 47) DOES NOT PROVIDE ENCRYPTION.** Traffic inside a GRE
tunnel is only as confidential as the underlying network path. If you
need confidentiality, add an encryption layer (WireGuard, IPsec, TLS)
independently — TixoLink does not provide this and does not market GRE
as a VPN. Some networks filter protocol 47; plan accordingly.

## Important limitations

- **No artifact signing.** Both the bootstrap installer and
  `tixolink update apply` verify SHA256 integrity of what they download,
  not publisher authenticity of the release channel itself. See
  "Public bootstrap installer" and the updater's trust-model section in
  [docs/lifecycle.md](../lifecycle.md).
- **HAProxy forwarding is TCP-only.**
- This is RC2: it has not run in a production environment. Report issues
  via GitHub's private vulnerability reporting (security issues) or a
  public issue (everything else).

## RC status

This build is a release candidate: feature-complete for the scope
described above and passing the full unit/integration/lifecycle test
suite (including the new bootstrap-installer tests), but not yet
declared production-stable.
